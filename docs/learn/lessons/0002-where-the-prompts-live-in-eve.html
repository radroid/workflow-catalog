Lesson 0002 · eve prompts

Where the prompts live in eve, and how to change one safely

One tangible win: you will be able to open the runner, find every prompt the workflow uses in under a minute, change one, and prove the change with a fixture before you commit.

1. Knowledge: prompts are files, and their paths are the API

eve derives everything from paths under agent/. That is good news for maintenance: there is no registry to update, and a prompt's location tells you what it controls.

Path in the runnerWhat it isWhen the model sees it
agent/instructions.mdThe always-on system prompt. "Whatever you write is the prompt."Every turn of every session
agent/skills/<name>/SKILL.mdA procedure the model loads on demand. Agent Skills format; description frontmatter is required.When the model decides the skill applies, or a tool loads it
agent/schedules/<name>.mdA cron prompt: frontmatter cron:, body is the task. Starts a new session on every fire.On the schedule, only under eve start
agent/subagents/<name>/instructions.mdSystem prompt of a delegated agentWhen the root agent delegates
agent/extensions/jobs.tsMounts the job-assistant package; its skills and prompts arrive prefixed jobs__As above, per contributed file
agent/tools/*.tsTool descriptions in defineTool({ description }). Not a prompt file, but the model reads them.Every turn, in the tool list

In this project the workflow's own prompts live in the package, packages/job-assistant/skills/*/SKILL.md, and the runner mounts them as an extension. So there are two places to look, and the prompt map lists both with the fixture that proves each one.

2. Knowledge: what a prompt change can and cannot be proven by

eve's test harness is evals/*.eval.ts run by eve eval. It can mock the model with mockModel from eve/evals, which is perfect for proving that tools get called correctly, and useless for proving that a prompt got better, because the mock ignores the prompt. So the rule in this repo is:

  1. Behaviour proofs (did the right tool get called, did the run refuse when unready) use mockModel evals and run in CI.
  2. Prompt proofs run the real model on a fixture and check the output with the deterministic validator: every claim cited, no excluded IDs, boundaries intact. They run locally with pnpm fixtures <name> and their output diff is attached to the commit.

Sources: eve evals overview, and the validator rules in docs/spec/mvp-spec.md §F7.

3. Skill: the change-one-prompt loop

  1. Find it. Open the prompt map, pick the file. Read the whole file, not just the line you want to change; skills carry a "Never" section that other sentences depend on.
  2. Find its fixture. The map names it. Run it once before you change anything so you have a baseline output.
  3. Change one thing. One instruction, one file. If you need two, that is two commits.
  4. Prove it. Re-run the fixture. Read the validator output and the diff against the baseline. If the validator got looser to make it pass, you changed the wrong thing.
  5. Commit with the proof. Message: which prompt, what you intended, the fixture name, and one line from the diff that shows it worked.

For interactive checks before writing a fixture, eve dev gives you the TUI, and eve invoke "…" gives you a single scripted turn from the shell. Source: eve dev TUI guide.

4. Retrieval practice

5. Do it for real

Pick the follow-up questions skill, packages/job-assistant/skills/follow-up-questions/SKILL.md. Baseline the onboarding fixture. Change the question the metric claim asks, so it requests the source of the number rather than a yes or no. Re-run. The validator should still pass and the diff should show the new question. Commit with the proof. Then write a learning record if anything surprised you.

Ask your teacherIf a fixture fails and you cannot tell whether the prompt or the validator is wrong, paste both outputs into this workspace and ask. The agent will diff them with you and say which one to change.
