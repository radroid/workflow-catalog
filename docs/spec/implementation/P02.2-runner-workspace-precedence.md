# P02.2 · The runner's workspace can't be redirected by the environment

Status: claimed (iter 006)
Assignee: iter-006 implementer (Sonnet)
Blocked by: none (P02 and P02.1 are done)
Owns:
- `runner/lib/settings.ts`: the workspace key's precedence, and the comment that documents precedence.
- `runner/lib/doctor.ts`: one warning.
- `runner/cli/*.ts` and `runner/lib/setup.ts` / `runner/lib/forget.ts`: only if a command resolves the workspace differently from `loadSettings`.
- New tests in `runner/test/`.
- `runner/README.md`: the matching lines only (the settings table, and doctor).
Spec: `logs/handoff/P04-round-2-review.md`, "`RUNNER_WORKSPACE` in production"; `logs/blocks.md`, "P04 peer review, round 2".

## Goal
A set-up runner always serves the workspace that `npm run setup` wrote to `runner/.env.local`. An ambient `RUNNER_WORKSPACE` can't redirect it: GitHub Actions sets one in every job, and a leftover shell export could set another.

## Background (found by the P04 round-2 reviewer)
- `loadSettings` lets any environment variable override `.env.local` (`settings.ts:98-108`). `runner`, `pair`, `ui`, `doctor` and `setup -- --forget` all take the workspace from it. Only setup's own workspace choice reads the file alone (`lib/setup.ts:202-207`).
- If the ambient value isn't a workspace, the runner fails closed with a misleading "Run `npm run setup`".
- If it names another valid workspace, the runner silently serves and writes that one:
  - pairing codes and sign-in links are issued against it;
  - doctor reports it healthy;
  - `--forget` would offer to delete it, and leave the configured workspace behind.
- The launcher hands eve `{...process.env, ...settings.values}` (`cli/runner.ts:75`), so eve's tools and the bridge always agree with each other. They just agree on the ambient folder.

## Deliverables
1. For the workspace key only, `.env.local` wins over the environment once setup has written it. The environment still supplies the workspace when `.env.local` has none, as for tests and a first run. Every other key keeps today's precedence, with the environment winning, as in eve.
2. `npm run doctor` adds one plain warning when the environment's `RUNNER_WORKSPACE` differs from `.env.local`'s. It names both paths and says which one the runner uses.
3. Every command resolves the workspace the same way: `runner`, `pair`, `ui`, `doctor`, `setup` and `setup -- --forget`.
4. The launcher still hands eve the resolved workspace, so the bridge and the agent's tools agree.
5. Update the precedence comment in `settings.ts` to name the exception and the reason.

## Acceptance
- **Tests:**
  - With `.env.local` naming workspace A and the environment naming a valid workspace B, every command resolves A, and doctor warns, naming both.
  - With no workspace in `.env.local`, the environment's B is used.
  - With the environment set to a folder that isn't a workspace, as GitHub Actions does, a set-up runner resolves A normally.
  - `--forget` targets A, never B.
- **Mutation proof:** restoring environment precedence for the workspace fails a test.
- **Chain:** `pnpm typecheck && pnpm test && pnpm -r lint && pnpm check:fixtures` is green, and CI is green.

## Out of scope
Renaming the `RUNNER_` prefix. GitHub Actions reserves `RUNNER_*`, so this is an owner question to settle before the first release. The eval workspace module (P04) and the agent's reads of `RUNNER_WORKSPACE` (the launcher-to-eve handoff) are also out of scope.

**The defect (found by the coordinator, in the shape of the W4 grant, not this round's work).** `cli/runner.ts`'s entry-point guard, `path.resolve(process.argv[1]) === fileURLToPath(import.meta.url)`, is unsound: Node resolves the main module's URL to its real, symlink-free path, but leaves `argv[1]` as typed. `path.resolve` does not canonicalize away a symlink, so on any symlinked checkout path — macOS `/tmp` → `/private/tmp`, or a symlinked home or code folder — the two sides disagree and the guard is false. `npm run runner` would exit silently without starting `main()`, with no error. No test and no CI step invokes the real `npm run runner` process, so nothing in the existing suite could have caught it.

**The fix.**
- New file `runner/lib/eve-env.ts` (granted for this by the coordinator) now holds `buildEveEnv` and `BuildEveEnvOptions`, moved out of `cli/runner.ts` verbatim (only the doc comment's cross-reference to "the command line below" became "the command line (cli/runner.ts)", since that line is no longer in the same file).
- `runner/cli/runner.ts` is restored to the merge-base (`6798e8c`) structure: `git diff 6798e8c -- runner/cli/runner.ts` now shows exactly three things — the `evePathEnv`/`PRIVACY_ENV` imports replaced by one `buildEveEnv` import from `../lib/eve-env.ts`, and the old three-line inline env construction (`{...process.env, ...settings.values, ...PRIVACY_ENV, PATH: evePathEnv(...)}` + two `delete`s) replaced by one `buildEveEnv({...})` call. No `main()` wrapper, no entry-point guard, no `path`/`url` imports — a plain top-level script again, same as the merge base and consistent with every other `runner/cli/*.ts` entry point (`doctor.ts` and `setup.ts` unconditionally `await main()`; `pair.ts`, `ui.ts` and `eval.ts` are plain top-level scripts too — none uses a guard).
