## Goal
Deliver the source modes P03 deferred, so every F4 category can be provided the way spec §4 names:
- a dropped PDF or DOCX;
- an exported data archive;
- a public page by URL;
- repositories through a read-only GitHub token.

## Deliverables
- **PDF and DOCX upload.**
  - Text is extracted locally in the runner. It goes nowhere except the extraction model call.
  - Libraries must be maintained, with no native build step, no install scripts and no network access. Pin exact versions, and report the choice and the reason.
  - Caps: file size (10 MB), extracted text (P03's per-source cap), and a time budget.
  - An encrypted or malformed file gives a plain error, never a crash.
  - The raw file lands under `sources/<category>/` with P03's file-name confinement.
- **Exported archives** (LinkedIn and similar, "uploaded as a file" per §4).
  - A ZIP is read in memory, never unpacked to disk.
  - CSV, TXT, MD and JSON entries become the source text.
  - Caps: entry count, per-entry size, total uncompressed size and compression ratio (zip-bomb guard).
  - Entry paths are never used as file paths.
- **URL import** (portfolio or site, and public profile pages the person owns).
  - Fetch through P04's `safe-fetch`: https only; no loopback, private, link-local or metadata addresses, checked after DNS resolution and on every redirect; a redirect limit, a size cap and a timeout; `text/html` or `text/plain` only.
  - Extract the text with P04's `readable-text`.
  - The fetched text is stored as the source file and extracted like any other source.
- **GitHub token** (the repositories category), read-only.
  - Use `gh auth token` when the gh CLI is signed in. Otherwise, a fine-grained PAT is pasted once and stored in the OS keychain through `runner/lib/secret-store.ts` (service `workflow-catalog-runner`, name `github-token`).
  - The token never appears in the workspace, the journal, logs, the UI or any response.
  - The runner reads the person's own repositories into one source text: name, description, languages, topics, and the README up to a cap.
  - `npm run setup -- --forget` lists and removes the keychain entry.
- **Local UI.**
  - The Onboarding page offers these modes per category, alongside paste and TXT/MD upload.
  - It keeps the focus, announcement and contrast rules from P03's revision.

### Gate fix round 1
Review: `/tmp/wc-manual/P03.1-gate-review.md` (2026-09-25). 4 BLOCKING (B1-B4); the FOLLOW-UPs are the orchestrator's, not fixed here. Each fix below has a test that fails without it (confirmed, then the fix restored) and a mutation proof (mutate the fix itself, confirm the same test fails, revert, confirm `git diff` clean).

- **B1 (regression — the note at the top stopped reappearing).** `refused()` (`onboarding.js`) and `run()`'s catch (`profile.js`) no longer drop the reload unconditionally. career-profile.md can be hand-edited to something unreadable *while the page is already open* (the reviewer's exact input: `ui-pages.test.ts`'s own `damageMarkdown`, run after the page's first load, then a source-status click); the write that discovers this refuses with "…See the note at the top." (`MARKDOWN_UNREADABLE_REFUSAL`), but that note's visibility comes only from a fresh `GET /api/onboarding`'s `markdownError`, which the refusal's own response never carries (`server/routes/onboarding.ts`'s own comment: "the file's problem is on the page already; a refused write only says so"). Both files now reload in the background — after announcing, never before, so the announcement never again waits on the write's own lock (carried item 1 stays fixed: 5.0 s, not ~10 s) — but only when the message promises the note (`SEES_MARKDOWN_NOTE = /see the note/i`) **and** `view` doesn't already carry it. That second condition isn't just an optimization: an unconditional reload was found, empirically, to reintroduce a real flake — its `load()` still goes through `store/profile-writes.ts`'s cross-process lock file, and a reload left running past a test's own completion could race `helpers.ts`'s workspace teardown (`ENOTEMPTY: directory not empty, rmdir ...`, reproduced 2 of 2 full-suite runs with the unconditional version, 0 of 2 with the condition added, confirmed by toggling only that condition). When the page loaded already damaged (`view.markdownError` set from the very first load), the note is already showing and a second reload has nothing new to reveal.
  - Test: `runner/test/onboarding-carried-items.test.ts` › "Gate fix round 1, B1: a refusal that names the note at the top makes that note appear" › "onboarding: career-profile.md is damaged after the page is already open; the next refused write reloads and reveals #markdown-problem".
  - Mutation proof: dropped the reload line in `onboarding.js` → the B1 test timed out waiting for the note (confirmed against both the original condition and the refined one); restored, `git diff` clean.

- **B2 (data loss — a URL import could overwrite an unrelated upload).** `urlUploadName()` (`server/routes/onboarding.ts`) now derives each import's file name from the *whole* URL — a readable host+path stem (path separators replaced before it ever reaches `ProfileStore`'s own "last path segment only" name handling) plus a short `sha256Hex` hash of the complete URL, capped well under `uploadFileName`'s 80-character limit so the hash suffix can never be truncated off. Re-importing the exact same URL still replaces the same file (the hash matches); two different URLs — even ones whose *last path segment* collides, or two different hosts' bare roots — never collide again, and "Replaced the earlier import" is said only when `before.includes(saved.fileName)`, which is now accurate because the file name is 1:1 with the URL.
  - Tests, the reviewer's exact two inputs: `runner/test/onboarding-sources.test.ts` › `POST /sources/:category/url` › "B2: an own resume.txt upload survives importing a URL whose last path segment is also 'resume'" and "B2: two site roots on different hosts each keep their own import, neither called 'Replaced'".
  - Mutation proof: reverted `urlUploadName` to build the stem from the raw, un-escaped `hostname + pathname` with no hash → both B2 tests failed exactly as the reviewer described (a false "Replaced", the person's own `resume.txt` overwritten, "upload.txt" collision); restored, `git diff` clean.

- **B3 (a DOCX zip bomb, and no per-source cap on any new extracted text).** `docxText` (`lib/document-text.ts`) now applies the identical guard `archive-text.ts` already applies to CSV/TXT/MD/JSON entries — entry count, per-entry uncompressed size (2 MB) and compression ratio (100:1), all read from the zip's own declared header metadata *before* fflate inflates `word/document.xml` — with the same numbers, so a DOCX doesn't get a more permissive guard than a ZIP. Separately, `extractedTextTooLarge()` now holds every new source's extracted text (file upload — PDF, DOCX or ZIP — and URL import) to the same 512 KiB per-source cap (`MAX_SOURCE_CONTENT_BYTES`) a pasted or `.txt`/`.md`-uploaded source already gets, refusing plainly (413 `extracted_text_too_large`) before saving. GitHub import was checked and left alone: 30 repos × a 2000-character README cap already bounds it well under 512 KiB.
  - Tests: `runner/test/document-text-extraction.test.ts` › "Gate fix round 1, B3: a DOCX zip bomb" (three tests: the ratio guard, the per-entry-size guard on barely-compressible bytes, and an ordinary DOCX unaffected); `runner/test/onboarding-sources.test.ts` › "413s an archive whose extracted text is over the 512 KiB per-source cap, even though it's inside every archive-text.ts cap" (the reviewer's second finding — the missing cap also affects archives).
  - Mutation proofs: (1) dropped the entry-count/ratio/size checks in `docxText`'s filter → both zip-bomb tests failed (returned "empty" instead of "zip_bomb" — the *other* fix, B4's linear regex, kept it from crashing or hanging, but the size itself went unchecked); restored, clean. (2) the route-level 512 KiB check isn't separately mutation-proofed beyond this — it's a single added `if`, and its own test already proves it (present vs. absent is the test itself failing/passing).

- **B4 (a malformed DOCX could block the event loop for unbounded time).** `RUN_TEXT`'s attribute-matching group changed from `[^>]*` to `[^<>]*` — real XML attribute values never contain a literal `<` either, so this changes nothing for a genuine document, but it means a failed match at one `<w:t ` can never scan past the *next* tag start looking for a `>` that isn't there, turning the old O(n²) (an O(n) scan repeated at each of O(n) start positions) into O(n). A per-paragraph wall-clock deadline (`bodyTextFromDocumentXml` now takes a `deadline` and checks `Date.now()` between paragraphs, returning `null` → a `timeout` refusal) is the backstop the reviewer asked for: JS can't preempt a synchronous regex mid-match, so this only helps *between* paragraphs, but it bounds any pathological shape this file didn't anticipate, not just the one reproduced.
  - Tests: `runner/test/document-text-extraction.test.ts` › "Gate fix round 1, B4" (two tests: the reviewer's exact shape — repeated, unclosed `<w:t ` — scaled to 300 KB, stored uncompressed so B3's own ratio guard can't short-circuit it, asserting `elapsed < 3_000` ms; and the per-paragraph deadline backstop with an injected `timeoutMs: 0`, using many small paragraphs so the check is guaranteed to land after the deadline rather than possibly landing in the same millisecond it was set).
